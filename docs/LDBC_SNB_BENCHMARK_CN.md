## 三、CSR 邻接索引架构

v1.1.0 6月版新增了按 RelationType 分文件的 CSR（Compressed Sparse Row）邻接索引：

- **存储格式**: `csr_{:04x}.bin` — 每关系类型独立 mmap 文件
- **数据结构**: 16 字节 `(NodeOffset, EdgeOffset)` 对，按源节点排序
- **写入维护**: `create_edge` 时同步追加，`create_edges_batch` 批量追加
- **启动构建**: `build_from_scan` 全量扫描已有边链，分组写入各类型 CSR
- **BFS 加速**: `read_filtered_edges` 直接从类型 CSR 读取邻居，无需逐边链遍历
- **Triangle Count 加速**: 从 CSR 直接构建邻接，消除链式遍历和 HashSet 去重

## 四、竞品水平对比

### 4.1 竞品参照

| 系统 | 类型 | SF1 覆盖率 | SunDaoQL 对比 |

### 4.3 硬件差异说明

本测试在 Apple M4 Max（16 核）上运行，与竞品常用硬件存在差异：

| | M4 Max | 竞品典型（Xeon 服务器） |
|------|---------|-----------------|
| 单核性能 | ⭐⭐⭐⭐⭐ 顶级 | ⭐⭐⭐ |
| 多核并行 | 16 核 | 32-128 核 |
| 内存带宽 | ~800 GB/s（统一内存） | ~400 GB/s（DDR5） |

M4 Max 的极强单核性能对单线程图遍历有利，但 16 核限制了并行 BI 查询的吞吐量。三角形计数类已并行化的查询（BI12/BI17）在 64 核 Xeon 上预计有 3-5 倍加速。

### 4.4 综合定位

**基于 LDBC 压测数据评分（仅比较覆盖率和延迟）：**

```
⭐⭐⭐⭐⭐  TigerGraph  — BI查询全秒级，十年商业产品
⭐⭐⭐☆    SunDaoQL   — IC全交互 + BI全覆盖 + 三角形计数可批处理
⭐⭐⭐      Neo4j     — IC强，BI仅 48% 覆盖（13/25跑不出来）
⭐⭐⭐      Kuzu      — 嵌入式图数据库，快查询多但个别退化严重
⭐⭐        PostgreSQL — 递归CTE硬做，覆盖率和性能都低
```

> **说明**：Neo4j 在 SF1 下 25 个 BI 查询仅完成 12 个，13 个超时或无法返回结果。SunDaoQL 在纯压测指标上（覆盖率、延迟）已超越 Neo4j。但 Neo4j 拥有 Cypher 生态、生产部署验证、查询优化器成熟度等 SunDaoQL 尚不具备的产品工程优势。两者在不同维度上各有领先，排名因评分权重而异。

## 五、工业制造场景

### 5.1 SunDAO 目标场景能力映射

SunDAO 的核心市场是工业制造（BOM/MRP/APS/MES/WMS/TMS），这些场景的查询负载与社交网络 BI9 完全不同。

| 工业需求 | 负载特征 | 对应 LDBC 查询 | P50 | 可用性 |
|---------|---------|-------------|:---:|:------:|
| 实体详情查询（设备/物料/工单） | O(1) 点查 | IC1 | 0.26ms | ✅ |
| BOM单层用料 | 1跳遍历 | IC5 模式 | 0.93ms | ✅ |
| BOM完整展开（10层） | 深度树遍历 | BFS × 10 | ~0.1µs/跳 | ✅ |
| 物料替代推荐 | 关系推荐 | IC3 模式 | 1.74ms | ✅ |
| 最短运输/搬运路径 | 最短路径 | IC13/IC14 | 0.05-0.64ms | ✅ |
| 按工厂统计产能 | 维度聚合 | BI1 模式 | 1.2s | ⚠️ 报表级 |
| 设备故障关联分析 | 多跳 + 过滤 | BI19 | 10.4ms | ✅ |
| 物料批次质量追溯 | SCAN + 过滤 + 遍历 | IC 类组合 | 毫秒级 | ✅ |
| 订单状态变更传播 | BFS 遍历 | 微秒/跳 | 微秒级 | ✅ |

### 5.2 核心负载特征差异

| 维度 | BI9（社交网络） | 工业制造查询 |
|------|--------------|-----------|
| 扇出模式 | 无界广播 × 二次爆炸 | 有界深窄树（BOM深度5-15，扇出10-50） |
| 数据量级 | 百万级交叉爆炸 | 千-万级确定路径 |
| 聚合方式 | 全局 GROUP BY + ORDER BY | 局部递归算术（每节点×用量×损耗率） |
| 时间约束 | 无边界 | 天然受工厂/产线/时段限定 |

**BI9 的 15 分钟性能局限不影响 SunDAO 工业制造核心场景。** 两者负载特征完全不同：BI9 是"从少数起点扇出到百万节点再全局聚合"，工业查询是"从确定起点沿有限路径深入，沿途做局部计算"。

## 六、知识图谱 / AI Memory / 语义网络 / 世界模型

SunDAO 的四个核心非工业场景，其查询模式同样与 BI9 存在本质差异。

### 6.1 场景能力映射

| 场景 | 典型操作 | 对应LDBC查询 | P50 | 可用性 |
|------|---------|-------------|:---:|:------:|
| **知识图谱** — 实体详情 | Being 点查 | IC1 | 0.26ms | ✅ |
| **知识图谱** — 关系路径 | 2-5跳遍历 | IC13/IC14/IC3 | 0.05-3.29ms | ✅ |
| **知识图谱** — 供应链穿透 | 多跳探索 | IC4 | 3.29ms | ✅ |
| **AI Memory** — 查最近对话 | 时序过滤 | IC2/IC8 | 0.16ms | ✅ |
| **AI Memory** — 记忆检索 | 关系推荐 | IC9 | 1.93ms | ✅ |
| **AI Memory** — 版本链追溯 | 历史版本遍历 | IC7 | 1.26ms | ✅ |
| **AI Memory** — 时间过滤 | 窗口过滤 | IC11 | 4.21ms | ✅ |
| **语义网络** — 概念邻居 | 1跳展开 | BFS | 微秒/跳 | ✅ |
| **语义网络** — 社交圈 | 多跳展开 | BI8 | 7.98ms | ✅ |
| **语义网络** — 模式查询 | 图模式匹配 | BI14 | 4.07ms | ✅ |
| **世界模型** — 信念传播 | BFS 遍历 | 微秒/跳 | 微秒级 | ✅ |
| **世界模型** — 加权交互 | 关系 + 权重过滤 | BI15 | 7.02ms | ✅ |
| **世界模型** — 时间窗口实体查询 | SCAN + 过滤 | IC11 | 4.21ms | ✅ |

### 6.2 核心结论

这四个场景的日常操作是**"从特定实体出发，沿有限关系类型，做 2-5 跳遍历，沿路径做局部计算或过滤"**。这是 IC 类查询的访问模式，压测中 90% 在 10ms 以内，大部分在亚毫秒级。

BI9 代表的"全图扫描 × 笛卡尔积扩张 × 全局聚合"在这四个场景的日常查询中**不存在**。BI9 的性能短板与 SunDAO 要服务的核心知识场景无关。

唯一需要关注的是 IC6 和 IC10（18-19秒），这两个深度多跳排序推荐查询目前是短板。但它们的查询模式（固定5跳以内的路径探索 + Top-K 排序）比 BI9 更可控，通过中间结果缓存和查询计划优化有明确的改善空间。

## 七、量化交易场景

### 7.1 场景匹配度

| 量化子场景 | SunDaoQL 适用度 | 说明 |
|-----------|:---:|------|
| **合规审计** | ⭐⭐⭐⭐⭐ | WAL 不可变追加 + 链式哈希 + REASONING_CHAIN 白箱推理，独有优势 |
| **多资产关联图谱** | ⭐⭐⭐⭐ | 图引擎多跳关系查询（"找出受汇率影响且持有海外资产>30%的所有A股"），毫秒级 |
| **因子研究** | ⭐⭐⭐ | 列引擎聚合可用，但非差异化 |
| **向量相似搜索** | ⭐⭐⭐ | 299µs HNSW 可用，未超越专业方案（Faiss等） |
| **策略回测** | ⭐⭐ | 仅数据层，回测是策略引擎的职责 |
| **实时行情接入** | ⭐ | 压测 1.8 QPS 远不足以支撑 tick 级行情接入（数万-数十万/s） |
| **低延迟信号执行** | ❌ | <1µs 确定性延迟需要 FPGA/kernel-bypass，非软件架构范畴 |
| **时序窗口函数** | ⭐ | 基础 LAG/LEAD 已实现，距专业时序库（kdb+ wj/aj/asof）差距显著 |

### 7.2 核心判断

SunDaoQL 在量化领域的真正差异化不是"更快的行情处理"——kdb+/QuestDB/自研 C++ 早已占据该赛道——而是**不可篡改的审计追踪 + 多资产关系图谱的组合**。金融机构在 SEC/证监会法规压力下愿意为这个组合付费，且目前无单一竞品同时覆盖这两点。
